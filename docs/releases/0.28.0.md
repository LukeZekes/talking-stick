# Talking Stick 0.28.0

Date: 2026-10-20

## Changed

- `talking-stick-rooms` is now a management workflow for overseeing rooms from outside, for example from a desktop app. It covers status from briefs; questions, instructions, follow-ups and relayed approvals sent with `tt room ask` and a reusable `--request-key`; relayed instructions that quote their source, time and scope without impersonating the user; and follow-up that reports stored, delivered, received and replied as separate facts. The main skill tells agents how to answer a visitor: accept, plan, or blocker, naming the rule when they need the operator's own confirmation.
- `tt room replies` reports `recipient_status` for each recipient: whether it is still in the room, the wake attempt that dispatched this request (while still on record), when its `tt` received the request, and whether it replied.

## Fixed

- `tt standby` no longer promises an automatic Codex wake after the local CLI reports that the session's thread is unknown. It keeps any working cmux fallback; a new session or successful native delivery restores the native capability.
- A wake that failed in the sending process no longer strands the message. When a failure is the sender's own (a denied socket connect, or a `codex` it could not launch), the work stays pending, and the next `tt` command on the host retries it. A delivery that could not be confirmed is retried after five minutes by the next `tt` command if its events are still unread, instead of only when another message arrives. Delivered batches still wait for the agent. Before this, a visitor question sent from ChatGPT reached the room but never woke its agents, and a quick follow-up didn't help.
- Any socket error before Claude's inbox connects now counts as a definite failure, since nothing was sent.
- An open `tt chat` delivers its room's pending wakes as new events arrive, and at least once a minute, instead of only when it closes. A question from ChatGPT, whose process may not open the agents' sockets, now reaches them within a minute while a console is open, usually within seconds.
- `tt room brief` marks visitor questions (`request_id`) and answers (`in_reply_to`), so an answer is no longer mistaken for a room broadcast.
- Delivery results and `tt health` show where a wake failed and the system's code (`connect:EPERM`, `spawn:ENOENT`, `exit:1 rpc:-32603`), drawn from a fixed list, so the next failure explains itself.

## Upgrading and limits

Run `tt self-update`, or let the daily automatic update install this release. Restart running
`tt chat` consoles to load the pending-wake relay, and reload the skills in existing harnesses.

Desktop sessions need access to the host's `tt` CLI. Visitor replies remain pull-only:
`tt room replies <request-id> --timeout 30` retrieves them; there is no automatic desktop
notification. A desktop Codex thread unknown to the local Codex CLI needs a parked listener
when participating as a member. `can_self_wake: false` now reports that limitation accurately.

## Verification

- Typecheck and build are clean; the full suite passes 950 tests with 1 skipped.
- Live Desktop Codex acceptance covered list/brief, a keyed retry returning the same request,
  a question and scoped instruction answered by terminal Claude, and a terminal Codex reply
  retrieved by Desktop. The Codex probe used a parked listener; it does not prove native idle wake.
- Desktop confirmed `can_self_wake: false` with no advertised transports for its unknown local
  thread. Isolated tests cover the running console's relay and restored wake capability.
- Delivery, recorded receipt and reply are separate evidence. Delivery is unknown when the
  retained attempt cannot be tied to the request; a missing receipt does not prove non-receipt.
